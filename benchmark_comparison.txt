NEW Implementation: UTF-8 safe truncation with utf8.ValidString() + utf8.RuneStart()

Platform: darwin arm64 (Apple M4 Pro)
Runs: 10 per test case

KEY OBSERVATIONS:
-------------------------------------------
1. Short strings (<100 bytes): Minimal overhead (5-13 ns, ~11-28%)
   - The utf8.ValidString() call is fast for short strings
   - The backup loop rarely executes (0-3 iterations max)

2. Long strings (>100 bytes): Notable overhead from utf8.ValidString()
   - utf8.ValidString() scans the entire string to validate
   - This is the dominant cost for longer strings
   - 900B CJK text: +396 ns, 1KB emoji: +328 ns

3. Invalid UTF-8: Fast path - skips boundary adjustment
   - Only ~4-5 ns overhead (just the ValidString check)

4. No truncation needed: Negligible overhead (~1 ns)
   - The check `len(stringVal) > limit` short-circuits

5. Memory: No additional allocations (same 48 B/op, 3 allocs/op)

CONCLUSION:
-------------------------------------------
The overhead is acceptable for correctness:
- Short strings (common case): <15 ns overhead
- Long strings: 300-500 ns overhead, still <1 microsecond
- Zero additional memory allocations

The fix ensures valid UTF-8 output, preventing downstream issues
with systems that expect valid UTF-8 strings.
